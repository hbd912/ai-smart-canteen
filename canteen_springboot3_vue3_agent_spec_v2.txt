AI 智慧食堂沉浸式点餐网页 产品需求说明与 Agent 实施规划（TXT）

文档用途 本说明文档用于交给代码 Agent。Agent
必须先检查现有项目架构、技术栈、路由、组件、静态资源配置和运行方式，再在不破坏现有项目的前提下实现本需求。本文定义产品流程、视频状态、交互规则、UI
视觉规范、页面布局、数据模型、验收标准。若项目已有成熟方案，优先复用；不得为了实现页面而无理由重建项目。

============================================================
一、项目目标与核心体验
============================================================

1.  产品定位 这是一个以沉浸式动画场景为核心的「AI
    智慧食堂」网页。用户不是在普通后台系统里点餐，而是通过一段连续的动漫风格食堂场景，体验男主进入食堂、落座、查看菜单、完成点餐、服务员送餐、开始用餐的完整过程。

2.  核心设计原则

-   视频是主场景，UI 是叠加在视频上的半透明交互层，不应让 UI
    抢走人物和场景的视觉焦点。
-   视频播放、暂停、切换、倒放必须由明确的业务状态驱动，不能仅依赖页面路由切换。
-   登录注册成功才允许从门口进入食堂。
-   是否结算决定是否进入“已点餐/用餐”状态。未结算时，桌面始终没有菜品。
-   只有在“未点餐、已落座”状态下点击“点餐”才播放/切换到菜单俯视镜头。
-   结算后播放送餐视频，再播放用餐视频；进入用餐状态后，场景固定，不再因点击导航而切回点餐镜头。
-   UI 必须响应式适配，但优先保证桌面端大屏演示效果，建议以
    16:9、1920×1080 为主要设计基准。
-   所有交互都要可操作、有反馈；不要制作只有视觉效果的假按钮。

3.  目标页面流程 初始进入网页 -> 播放 001-1：男主走向食堂并停在门口 ->
    展示登录/注册浮层（人物不能被遮挡） -> 登录或注册成功 -> 播放
    002-1：男主开门进入食堂 -> 播放 003-1：男主走到空座位并坐下 ->
    显示首页 UI（男主在画面右侧，左侧留出 UI 区域） -> 点击导航“点餐” ->
    播放 004-1 / 进入俯视菜单镜头，展示点餐 UI ->
    用户选择菜品并点击“去结算” ->
    若取消/返回/未完成结算：不算点餐成功，桌面无菜，回到未点餐状态 ->
    若结算成功：播放 005-1 服务员送餐 -> 播放
    006-1：男主开始用餐，镜头由俯视过渡到侧面 -> 显示用餐状态
    UI：左侧“正在用餐/珍惜粮食”等信息，禁止继续下单

3.  媒体资源处理要求

-   扫描 Animation 文件夹，按文件名匹配 001-1 至 006-1，识别
    mp4、webm、mov 等真实格式。
-   检查视频是否有黑边、播放器
    UI、水印、异常首尾帧；网页中只展示视频画面本身，不展示本地播放器控制条。
-   预先读取每段视频时长、宽高、帧率、编码、音轨信息。建立资源清单。
-   统一采用 object-fit: cover 或
    contain，不能随意裁掉人物头部、手部、托盘、菜单等关键主体。优先根据素材原始比例确定展示区域。
-   视频播放结束事件必须触发状态变化；不能用固定 setTimeout
    猜测视频结束时间。
-   关键镜头需要支持精准
    seek（跳转到指定时间），如项目浏览器环境不支持可靠倒放，则使用倒序帧序列、预生成反向视频，或设计平滑淡出/切回方案。不要假装
    video.playbackRate = -1 一定可用。
-   视频切换时避免黑屏闪烁：可使用双 video
    层、预加载下一段、首帧就绪后切换、短暂交叉淡化。
-   默认静音自动播放，以确保浏览器自动播放策略可用；如需声音，提供明确的音量开关。若视频没有必要音轨，默认静音。

三、整体页面结构与视觉风格
============================================================

1.  视觉关键词
    日系动漫电影感、温暖阳光、柔和景深、奶油白、浅米色、鼠尾草绿、暖棕色、玻璃拟态、圆角卡片、低饱和、轻量阴影、精致留白、生活化沉浸场景。

2.  风格方向

-   场景：以视频原画为背景，保持动漫食堂的暖色调，不额外叠加重度滤镜。
-   UI：半透明乳白玻璃卡片，背景模糊适中，边缘细腻，避免过度透明导致文字难读。
-   主色：鼠尾草绿/橄榄绿，用于主按钮、选中导航、确认状态。
-   辅色：奶油白、暖米色、浅杏色。
-   强调色：少量橙金色，用于价格、热量、提醒、标签。
-   文本：深咖灰/墨色，避免纯黑大面积使用。
-   圆角：卡片 18–26px；按钮 999px 胶囊或 12–16px；商品图片 14–18px。
-   阴影：柔和、低对比度、扩散型阴影。不要使用厚重黑色投影。
-   字体：优先使用系统中文无衬线字体，如“Microsoft YaHei”“PingFang
    SC”“Noto Sans SC”；标题字重 600–700，正文 400–500。
-   图标：统一线性或轻拟物图标风格。导航图标尺寸、线宽一致。可使用项目已有图标库；不要混用多套图标风格。
-   动效：缓动曲线柔和，常规 UI 过渡
    180–300ms；视频转场以素材自然剪辑为主，UI 淡入淡出 250–450ms。

3.  页面画布与布局安全区

-   主设计尺寸：1920×1080，宽屏 16:9。
-   视频背景铺满主视口，保持主体位置与参考图一致。
-   顶部导航高度约 72–84px，左右边距 28–40px。
-   左侧垂直导航宽度约 72–88px，距离左边缘 24px，上下居中或从顶部 250px
    左右开始。
-   UI 卡片与屏幕边缘至少留 24px 安全距离。
-   不能把登录框、首页卡片、点餐面板放到男主脸部、身体、手部、餐盘、桌面关键区域上。
-   小屏适配时允许卡片滚动或折叠，但不能遮住视频主体；必要时缩小视频展示比例或调整
    UI 布局，不允许关键交互被裁掉。

4.  公共 UI 组件 A. 顶部品牌栏

-   左侧：绿色食堂/叶片 Logo + “智慧食堂”文字。
-   品牌后可放细分隔线和轻提示语“今天想吃点什么？”。
-   中间：搜索框，可输入菜品名称、口味或营养需求。
-   右侧：天气/温度与日期（若无真实天气接口，显示静态演示数据并标注为演示，不要伪造实时数据）、通知铃铛、用户头像。
-   顶栏采用白色半透明磨砂背景，圆角胶囊容器，轻微阴影。

B. 左侧垂直导航 固定五项，顺序不可改变： 1. 首页（home） 2.
点餐（utensils） 3. 订单（calendar/list） 4. 收藏（star） 5.
营养管理（chart/bar-chart）

导航表现： - 竖向白色半透明圆角胶囊底板。 -
每项图标居中，默认绿色描边/深绿。 -
当前选中项使用深鼠尾草绿圆形或胶囊底，图标反白。 -
鼠标悬停时轻微放大或背景加深。 - 每项有 tooltip
或文字标签，保证可识别。 -
不同业务状态下，导航点击行为必须按“状态机与导航规则”执行，不允许直接随意切换视频。

C. 内容卡片 - 半透明暖白底，背景模糊 12–20px 左右，透明度需确保可读。 -
卡片标题带小图标，标题下可有一句简短说明。 - 卡片内边距
20–28px，卡片间距 14–20px。 -
信息层级明确，不要将所有内容堆在同一块卡片里。

四、各阶段页面与 UI 详细设计
============================================================

阶段 A：初始进入 / 001-1 门口画面 / 登录注册

视频行为： - 首次打开网页，立即加载并播放 001-1。 -
视频从头播放，男主走向食堂。 - 001-1
播放到结尾时，停留在图1对应的门口画面。 -
不要在视频播放期间提前弹出登录框；可以在视频接近结束时预加载登录
UI，但必须等到结尾后再展示。 - 结束后保持最后一帧，不自动循环。

登录注册 UI： - 使用右侧浮动玻璃卡片，建议宽度
360–420px，高度按内容自适应。 - 位置：画面右侧中部，右边距
5%–7%，垂直居中略偏上。 -
图1人物位于中间偏左区域，因此登录卡片不得覆盖男主身体、头部和入口门把手；Agent
应以真实视频截图校准位置。 - 卡片标题：“欢迎来到智慧食堂”。 -
副标题：“登录后开启你的智能用餐体验”。 -
登录模式字段：账号/手机号或邮箱、密码；提供“记住我”（可选）、“忘记密码”（若无后端则展示可交互提示，不要做无效跳转）。 -
注册模式字段：昵称、账号/手机号或邮箱、密码、确认密码；勾选用户协议（演示版本可使用本地状态）。 -
主按钮：“登录”或“注册并进入”。 - 底部提供“没有账号？立即注册 /
已有账号？立即登录”切换。 -
表单校验：必填、格式、密码一致性、协议勾选；错误提示显示在字段下方。 -
成功登录后：关闭卡片，播放 002-1。 -
若没有后端认证接口，采用明确的演示模式本地验证（例如任意非空账号 +
满足长度的密码），并在代码中隔离
AuthService，方便以后接入真实接口。不得声称已经接入真实账号体系。 -
登录成功后保存本次会话状态，刷新页面是否保持登录由项目架构决定；演示版可使用
sessionStorage，不存明文密码。

阶段 B：开门进入 / 002-1

-   登录成功后触发 002-1，从头播放。
-   登录卡片完全退出，避免与视频叠加。
-   此阶段不显示完整业务导航和点餐 UI；可以保留极简品牌
    Logo，不显示会干扰观影的卡片。
-   视频结束后自动播放 003-1。
-   若 002-1 加载失败，显示简洁错误提示与“重试”，不能卡死在空白页面。

阶段 C：首页 / 003-1 落座 / 未点餐状态

视频行为： - 播放 003-1，男主走到座位并坐下。 - 003-1
结束后停留在最后一帧，保持图2构图。 -
这是未点餐默认首页场景：男主在画面右侧，左侧留白用于 UI。 -
视频不循环，不自动切换其他视频。 - 顶部导航与左侧导航在视频结束后淡入。

首页 UI 参考图3，布局： - 顶部公共品牌栏。 - 左侧公共垂直导航。 -
主内容只放在画面左侧约 55%–62% 宽度区域；右侧男主区域尽量不叠加卡片。 -
顶部主卡片：AI 智能推荐入口。 标题：“今天吃什么？让我帮你搭配”
描述：“告诉我你的饮食需求，我来为你推荐合适的美味～”
快捷标签建议：减脂轻食、增加蛋白、清淡健康、快速饱腹。
输入框占位文案：“例如：我今天运动了，想吃得清淡一点……” 右侧或卡片内放 AI
厨师机器人插画（如果项目中没有素材，可用简洁机器人图标/插画占位，不要生成与整体画风冲突的素材）。
点击快捷标签或输入问题后，展示推荐回复，可用本地模拟数据；若无 AI
服务，不得伪装真实 AI 接口已接通。 - 中部左侧“今日推荐”卡片：横向 3
个菜品卡片，展示菜品图、名称、价格、热量、加入购物车按钮；其中一个可有“人气
TOP”或“今日推荐”标签。 -
中部右侧“今日营养分析”卡片：圆环/进度展示今日目标达成率，列出热量、蛋白质、饮水量等指标。数据为演示数据时需在代码中标注
mock。 -
底部“食堂菜品分类”卡片：主食套餐、荤菜、素菜、面食、汤品、饮品等分类入口。 -
右下角可放迷你购物车摘要，但不能遮挡男主主体；若空间不足，移动至左侧内容区域底部。 -
首页卡片应有清晰层级：AI
推荐最大，其次今日推荐/营养分析，分类区作为底部入口。 -
首页默认展示空桌视频画面，购物车可有临时选择，但只要未结算成功，桌面仍然是空的。

首页导航行为： - 点击“首页”：保持当前 003-1 最后一帧，不重新播放
003-1；若处于点餐镜头且尚未结算，按状态规则回到 003-1 的落座画面。 -
点击“订单”：显示订单信息面板/订单历史，不改变当前视频视角；未下单时显示空状态。 -
点击“收藏”：显示收藏菜品面板，不改变当前视频视角。 -
点击“营养管理”：显示营养分析面板，不改变当前视频视角。 -
点击“点餐”：满足“未点餐且已落座”条件时，触发 004-1。

阶段 D：点餐 / 004-1 俯视镜头 / 菜单选择

触发条件： - 用户已登录。 - 003-1
已播放完成并进入“已落座、未点餐”状态。 - 当前尚未结算成功。 -
用户点击左侧导航“点餐”。 - 点击后先切换选中导航，再播放
004-1；不能先显示完整菜单 UI 再让视频晚一步。

视频与布局： - 播放 004-1，展示从原本侧面/常规视角转为俯视角的过程。 -
结束后停留在图4构图：男主位于画面左侧/左下区域，桌面菜单清晰可见，右侧空间用于点餐面板。 -
若 004-1 本身结尾已是稳定俯视构图，则直接停留最后一帧。 - 点餐 UI
使用图5布局参考，放在画面右侧，建议占视口宽度 55%–60%，高度
78%–82%，顶部距公共导航栏 20px。 -
左侧人物、桌面、菜单区域应保留可见，面板不得压到男主头部和菜单关键区域。 -
左侧导航仍固定显示，点餐项选中。 - 顶部品牌栏保留。

点餐页面 UI： - 面板标题：“今日菜单” -
副标题：“新鲜美味，为你准备好了” - 顶部右侧排序/筛选控件： 1.
销量优先（默认） 2. 价格排序（升序/降序） 3. 热量筛选（区间/低热量） -
分类横向标签：全部菜品、主食套餐、荤菜、素菜、面食、汤品、饮品。 -
菜品采用 3 列网格卡片（宽屏），每张卡片包含： - 菜品大图，比例约 16:9 或
1.7:1，圆角 14–18px。 - 菜品名称。 - 价格（橙棕色强调）。 - 热量
kcal（灰色次级信息）。 - 右下角绿色圆形“+”按钮。 -
可选标签：人气推荐、低脂、今日推荐。 -
商品卡片统一高度，图片裁切规则一致。 -
推荐示例菜品可沿用参考图中的名称：黑椒鸡排饭、番茄牛腩饭、香菇滑鸡饭、宫保鸡丁饭、鱼香肉丝饭、清炒时蔬。价格与热量仅作为演示数据，统一放在
mock 数据文件中，不能散落硬编码在组件里。 -
加入菜品后，“+”变为数量步进器（- 数量 +），购物车摘要实时更新。 -
点击菜品图片或名称可打开详情弹窗：菜品图片、简介、主要食材、过敏原提示（若数据未提供则显示“信息暂缺”）、热量、价格、加入购物车。 -
分类、排序、热量筛选必须真实改变列表数据。 - 搜索框可过滤菜品名称。 -
空结果要有清晰空状态与清除筛选入口。

购物车与结算： - 面板底部固定结算条，滚动菜品列表时结算条保持可见。 -
展示“已选 N 道菜品”、合计金额、按钮“去结算”。 -
未选择菜品时，“去结算”禁用。 -
点击“去结算”打开确认弹窗/结算抽屉，列出菜品、数量、小计、总价。 -
用户点击“确认下单/确认结算”才算结算成功。 -
点击关闭、取消、返回均不算成功；不触发 005-1 或 006-1。 -
结算成功时锁定购物车快照，生成订单号（演示环境可用本地生成
ID），保存订单记录，清空可编辑购物车或转为已提交状态，然后播放 005-1。 -
结算成功后不允许重复结算同一订单。

阶段 E：送餐 / 005-1

-   结算成功后，点餐面板和结算弹窗淡出，避免挡住服务员与托盘。
-   播放 005-1，从服务员端托盘走来、放置餐食的过程。
-   播放期间仅保留低干扰品牌标识，不显示可点击的点餐控件，不允许再次下单。
-   视频结束后自动播放 006-1。
-   005-1
    播放失败时提供重试；若无法恢复，可显示“餐食已送达（演示状态）”并允许进入用餐画面，但必须保证订单状态一致。

阶段 F：用餐 / 006-1 / 已结算、用餐中状态

视频行为： - 播放
006-1，表现男主开始用餐，包含俯视转向侧面视角的变化。 -
播放结束后停留在图7对应的侧面用餐画面。 -
画面中男主在右侧/偏右，桌上有餐盘和饮品，人物正在吃饭。 -
最终画面保持静止，不循环、不自动重新播放。 -
这是最终用餐场景。用户在订单、收藏、营养管理、首页之间切换时，背景始终保持图7的用餐画面，不再切换成图2或图4。 -
点击“点餐”也不触发 004-1，不允许继续加菜或重新下单。

用餐状态 UI： - 与首页相反，主要内容放在画面左侧约 40%–48%
区域，右侧男主和餐食保持完整可见。 -
参考首页的奶油白玻璃拟态，但视觉更轻、更克制。 -
左侧主卡片标题：“正在用餐” - 副标题：“好好享受这一餐，记得珍惜粮食。” -
显示订单摘要：菜品名称、数量、订单金额、下单时间（演示数据）。 -
显示提示卡片：“按需取餐，珍惜粮食；光盘行动，从每一餐做起。” -
可显示“本餐营养概览”：热量、蛋白质、蔬菜摄入等，基于订单菜品 mock
数据计算；数据不足时标注估算。 -
点餐导航仍可点击，但点击时只显示轻提示：“你正在用餐，请先享用当前餐食”，不改变视频、不打开点餐面板、不触发
004-1。 -
订单导航可查看当前订单详情；收藏和营养管理正常切换对应面板；首页显示用餐中的首页/订单摘要，但背景仍是图7。 -
若有“结束用餐”功能，必须作为明确的独立操作并二次确认；本需求未要求自动结束用餐，不得自行设定自动结束时间。

五、状态机与导航规则（必须严格实现）
============================================================

1.  核心状态定义
    建议使用一个集中式状态管理，不要让各组件各自维护互相冲突的状态。

-   INTRO_PLAYING：001-1 播放中
-   LOGIN_REQUIRED：001-1 结束，等待登录/注册
-   ENTERING：002-1 播放中
-   SEATING：003-1 播放中
-   HOME_IDLE：003-1 结束，已落座、未点餐、空桌
-   MENU_TRANSITION：004-1 播放中
-   MENU_OPEN：004-1 结束，俯视点餐页面
-   CHECKOUT_OPEN：结算确认弹窗打开
-   DELIVERY：005-1 播放中
-   EATING_TRANSITION：006-1 播放中
-   EATING：006-1 结束，已点餐、用餐中

另设 activePanel： - home - order - favorites - nutrition - menu

另设 orderStatus： - none - cart_only（仅购物车选择，尚未结算） -
submitted（已确认结算） - delivered（送餐完成） - eating（用餐中）

注意：activePanel 只是 UI 面板状态，不应直接决定视频状态。sceneState
才是视频和场景状态的唯一依据。

2.  核心转移规则

-   初次加载 -> INTRO_PLAYING。
-   001-1 ended -> LOGIN_REQUIRED。
-   登录成功 -> ENTERING。
-   002-1 ended -> SEATING。
-   003-1 ended -> HOME_IDLE，activePanel=home。
-   HOME_IDLE 点击点餐 -> MENU_TRANSITION，随后 MENU_OPEN。
-   MENU_OPEN 点击首页/订单/收藏/营养管理：
    -   如果尚未确认结算：关闭菜单面板，回到 003-1
        的落座空桌画面（HOME_IDLE），背景保持空桌。
    -   不要倒放整段 004-1 后又回放 003-1；优先用 003-1
        已缓存的结尾帧/暂停帧恢复。若产品确实需要镜头回退，使用预生成反向视频或倒序帧，不要依赖不稳定的原生负播放速率。
    -   切换目标面板（如订单/收藏/营养管理）时，背景仍为 003-1
        空桌画面。
-   MENU_OPEN 点击点餐：保持菜单页面，不重复播放 004-1。
-   CHECKOUT_OPEN 点击取消：回到 MENU_OPEN，购物车保留。
-   CHECKOUT_OPEN 点击确认结算：orderStatus=submitted，进入
    DELIVERY，锁定订单数据。
-   DELIVERY ended -> EATING_TRANSITION。
-   EATING_TRANSITION ended -> EATING，orderStatus=eating。
-   EATING 状态点击首页/订单/收藏/营养管理：只切换对应 UI
    面板，背景永远保持图7。
-   EATING 状态点击点餐：不切换场景、不显示菜单、不播放
    004-1；给出“正在用餐，暂不可继续点餐”的提示。
-   页面刷新时根据已保存会话/订单恢复合理状态；至少不能出现已提交订单却回到空桌且允许重复下单的矛盾。演示版可将
    sceneState、订单和购物车保存到 sessionStorage 或
    localStorage，按项目安全规范实现。

3.  未结算回退的关键要求
    用户特别强调：若没有结算，男主就没有点餐。此时桌面必须一直没有菜。

-   仅加入购物车不代表已点餐。
-   打开结算确认弹窗不代表已点餐。
-   只有用户明确点击“确认下单/确认结算”才改变业务状态。
-   如果在菜单页没有结算就点击首页或其他导航，必须退出菜单视角，回到
    003-1 空桌画面。
-   不允许把 005-1 或 006-1 当作未结算的后续视频。
-   不允许在未结算状态显示桌面有菜的图7画面。
-   回退后购物车是否保留：默认保留购物车中的临时选择，用户再次进入点餐仍可继续选择；但订单状态仍是
    none/cart_only。若项目实现清空购物车，必须有明确提示；推荐保留。

4.  视频控制器实现要求 建议建立 SceneVideoController，统一负责：

-   视频资源映射与预加载
-   当前视频 source
-   play、pause、seek、切换
-   onEnded 状态回调
-   错误处理与重试
-   最后一帧保持
-   切换过程防止重复触发
-   防止组件重渲染导致视频意外从头播放

建议用状态机或 reducer 管理转移。每段视频的 ended 回调必须验证当前
sceneState 和
videoId，防止旧视频事件误触发后续状态。播放动作应幂等：同一状态重复点击不能重复启动同一段视频。

七、交互细节与异常处理
============================================================

1.  视频加载

-   显示简洁的加载状态，不显示浏览器默认 video 控件。
-   首次进入可先显示品牌 Logo 和柔和加载提示。
-   视频加载失败提供重试。
-   切换下一段视频前预加载下一段，避免停顿。
-   监听 loadedmetadata、canplay、playing、ended、error。
-   页面切后台时可暂停或保持播放，按项目体验统一处理；回到前台不能重复触发
    ended。

2.  登录注册

-   密码输入默认隐藏，可切换显示。
-   Enter 键可提交。
-   表单错误在对应字段下方展示。
-   登录成功后按钮显示短暂 loading，防止重复提交。
-   演示认证逻辑独立封装。

3.  点餐

-   数量最小为 0，最大数量可设为 99。
-   购物车数量、金额、热量实时汇总。
-   菜品筛选、排序、搜索可组合使用。
-   删除购物车商品时同步更新结算条。
-   结算弹窗必须显示清晰的最终金额。
-   防止连续点击确认造成重复订单。

4.  订单

-   未下单显示空状态：“还没有订单，去挑选今天的美味吧。”
-   已下单显示订单编号、菜品、数量、金额、状态和时间。
-   演示支付不应展示真实支付成功文案，除非已接入支付服务。

5.  收藏

-   菜品可收藏/取消收藏。
-   收藏状态在首页推荐卡和菜单卡片之间同步。
-   空收藏显示友好提示。

6.  营养管理

-   展示热量、蛋白质、脂肪、碳水、蔬菜摄入等指标。
-   若只有菜品估算数据，清楚标记“估算值/演示数据”。
-   不要将模拟数据表述为用户真实健康数据。

7.  可访问性

-   所有按钮具备可读名称、键盘焦点态。
-   表单字段有 label。
-   文字与背景对比度足够。
-   不仅依赖颜色表达选中/错误状态。
-   动效尊重 prefers-reduced-motion。

八、响应式适配规范

第七步：自测与交付 - 按第十节验收用例逐项测试。 -

十三、动态化体验升级（新增：全站必须有生命感，避免静态网页）
============================================================

本节是对前文视觉与交互要求的强化补充。Agent 必须把网页做成“可交互的动漫场景体验”，而不是把几张静态卡片叠在视频上。动态效果必须服务于叙事、信息层级和操作反馈，不能为了动而动。

1. 全站动效总原则
- 页面进入、模块出现、卡片悬停、导航切换、购物车变化、弹窗打开、数据更新，都应有自然且细腻的动效。
- 动效风格：日系动画电影的柔和感 + 现代产品 UI 的流畅感。避免夸张弹跳、频繁闪烁、强烈霓虹、廉价旋转和大面积粒子特效。
- 动效要有层次：背景视频是第一层动态；光影/氛围层是第二层；UI 卡片和交互反馈是第三层。
- 视频本身已经有动作时，UI 动效要克制，不能同时让所有卡片持续漂浮。
- 任何动画都不能妨碍阅读、点击和键盘操作。
- 页面切换要保持连续性，不能整个网页闪白、突然重排或出现明显黑屏。
- 对 prefers-reduced-motion 用户提供减弱动效方案，保留必要状态反馈。
- 所有动画应尽量使用 transform、opacity，避免频繁触发布局计算；注意性能和低配设备。

2. 全局氛围动态
建议实现以下轻量动态层：
A. 柔和环境光
- 在视频上方叠加极淡的暖色光晕/径向渐变，透明度低。
- 光晕可缓慢改变位置或透明度，周期约 12–20 秒，不可明显干扰视频。
- 不要覆盖人物脸部或菜品主体。

B. 玻璃卡片呼吸感
- 普通卡片默认保持稳定，不做持续大幅漂浮。
- 首次出现时做 12–18px 的轻微上移 + 淡入。
- 重点推荐卡片可做极轻微的 2–3px 浮动，周期 5–7 秒，错开动画起始时间。
- 鼠标悬停时卡片上浮 3–5px，阴影略增强，边框亮度略提升。
- 移开后平滑复位。

C. 光影与背景细节
- 可增加低透明度、缓慢移动的光斑或树影质感，但必须确保不与原视频光影冲突。
- 不要用高密度粒子、雪花、星星等与食堂主题无关的装饰。
- 不要把图片背景做成持续明显缩放，否则容易产生晕动感。

D. 页面滚动
- 内容区滚动时，卡片可做轻微视差或渐入，但必须保持滚动流畅。
- 顶部栏可在滚动时轻微收紧高度/增强背景不透明度。
- 不允许滚动触发视频重新播放。

3. 页面进入与模块出现动效
- 首次加载：品牌 Logo 轻微缩放淡入，随后视频淡入；加载过程展示简洁的“正在进入智慧食堂…”提示。
- 登录卡片：从右侧 24–36px 位置滑入并淡入，时长 350–500ms；不允许从屏幕外大幅飞入。
- 登录成功：卡片轻微缩小淡出，随后启动 002-1。视频开始前不要出现长时间空白。
- 首页 UI：顶部栏、侧边导航、AI 推荐卡、今日推荐、营养分析、分类卡片按层级依次淡入/轻微上移，错开约 60–100ms。
- 点餐页：右侧菜单面板从右侧 24px 轻滑入，菜品卡片按网格顺序轻微错峰出现；不要每次筛选都大幅重新飞入。
- 送餐阶段：点餐 UI 先淡出，视频 005-1 再开始；送餐结束后用餐 UI 淡入。
- 用餐页面：左侧“正在用餐”卡片轻微淡入，菜品/订单摘要以简洁数字递增或进度条填充展示。

4. 导航交互动效
- 当前选中导航图标可做 1.04–1.08 倍的轻微缩放，背景色平滑过渡。
- 点击导航时图标可有一次轻微按压反馈（scale 0.94 -> 1）。
- 选中指示器使用平滑位移或背景过渡，不要突然跳变。
- tooltip 延迟约 350–500ms 出现，淡入并轻微上移。
- 在用餐状态点击“点餐”时，不触发导航选中态切换为点餐页；可短暂出现轻微提示反馈，但不改变场景。
- 普通导航切换时，只切换内容面板，不重播背景视频。

5. 卡片、按钮与表单动效
- 主按钮 hover：亮度轻微增加、向上移动 1–2px；active：缩小到 0.97–0.98。
- 次按钮 hover：背景渐变或边框加深。
- 菜品卡片 hover：图片 scale 1.025–1.04，卡片上移 2–4px；图片必须被圆角容器裁切。
- “加入购物车”：加号按钮短暂变为勾选/数量状态，购物车角标数字滚动或弹性更新一次。
- 数量加减：数字使用轻量数字过渡，不能抖动布局。
- 收藏按钮：星形图标短暂缩放并填充颜色，状态持久化。
- 输入框 focus：边框变为鼠尾草绿，出现柔和外发光；错误状态短暂强调对应字段，不使用整屏震动。
- 表单提交：按钮显示 loading 状态，防止重复提交。

6. 动态数据展示
- 今日营养分析圆环：首次进入时从 0 平滑增长到目标百分比，约 800–1200ms。
- 热量、蛋白质、饮水量等数字可做一次递增展示；后续数据变化时平滑过渡。
- 购物车金额、数量、订单统计变化时使用轻量数字过渡。
- 进度条、圆环和小型图表均应根据实际数据驱动，不可只播放装饰动画。
- 若数据是 mock，UI 或代码中应明确标注演示数据。

7. 动效技术建议
- 先检查项目已有动画库，优先复用现有依赖。
- React 项目可评估 Framer Motion / Motion；Vue 项目可使用 Vue Transition、CSS transition 或项目已有动画方案；不得为了少量动画引入体积很大的新依赖。
- 使用统一 motion tokens，例如：
  --motion-fast: 160ms;
  --motion-normal: 240ms;
  --motion-slow: 420ms;
  --ease-standard: cubic-bezier(0.2, 0.7, 0.2, 1);
  --ease-enter: cubic-bezier(0.16, 1, 0.3, 1);
- 对长时间循环动效设置低频率、低幅度；避免多个无限动画叠加。
- 动画结束后必须处于稳定状态，不允许循环闪动。

1. 后台定位与入口
除普通用户的沉浸式智慧食堂前台外，新增一套独立的管理员管理后台。管理员后台用于管理菜品、分类、库存/供应状态、订单、用户、首页推荐内容和营养信息。

- 普通用户前台仍以动漫视频场景为核心，不显示后台管理菜单。
- 管理员登录入口放在登录卡片底部的小字链接“管理员入口”，或登录页右上角低调入口；不要占据主视觉。
- 点击后进入独立的管理员登录页面/弹窗，不要与普通用户登录混为一套表单。
- 管理员认证成功后进入后台管理工作台。
- 管理员后台与用户前台使用同一套菜品、分类、订单数据模型；不能做两份互不关联的数据。
- 普通用户不能通过修改前端路由或 localStorage 中的 role 就获得管理员权限。演示项目可做角色模拟，但必须把权限校验集中封装，并在交付说明中标记为 demo；真实部署必须由后端鉴权和接口权限控制。

2. 管理后台整体视觉
后台不使用动漫视频作为主背景，避免影响高频管理操作。保持与前台同一品牌语言，但更偏清晰、高效的运营控制台：
- 主背景：暖灰白/浅米色。
- 左侧固定深鼠尾草绿或浅色侧边栏。
- 顶部白色工具栏：页面标题、全局搜索、通知、管理员头像与退出。
- 内容区采用白色/奶油白卡片，圆角 14–20px，轻阴影。
- 主色沿用鼠尾草绿，橙色作为库存不足、待处理订单等提醒色。
- 图表和数据卡片简洁，避免高饱和、多彩渐变。
- 后台也应有适量动效：侧栏展开收起、路由切换、卡片加载、表格 hover、状态更新、抽屉/弹窗开合、图表加载；动效比前台更克制，以效率为先。

- delivered：已送达（005-1 完成）
- eating：用餐中（006-1 完成）
- completed：已完成（需明确触发，不自动假定）
- cancelled：已取消
管理员可按权限更新状态，但必须保证用户前台场景状态不会被随意改乱。
若管理员后台手动把订单标记为送达/完成，前台演示状态需要有一致的处理策略；不得让订单数据与视频状态冲突。

10. 用户管理

11. 首页推荐管理

- 设置推荐菜品、排序、推荐标签、人气 TOP、今日推荐。

17.2 固定技术栈与版本建议
------------------------------

后端：
- Java 17 或更高兼容版本。
- Spring Boot 3.x（使用与 JDK 版本兼容的稳定 3.x 版本；不要使用 Spring Boot 2.x）。
- Spring Web：提供 RESTful API。
- Spring Security：认证、授权与接口保护。
- JWT：用户登录后的无状态身份凭证；明确 Token 过期和退出登录处理。
- MySQL 8.x：关系型数据库。
- MyBatis-Plus 或 Spring Data JPA：数据访问层。建议本项目选择 MyBatis-Plus，避免同时混用多套 ORM。
- Jakarta Bean Validation：参数校验。
- springdoc-openapi / Swagger UI：生成接口文档，便于课堂演示接口。
- Maven：项目构建与依赖管理。
- BCrypt：密码哈希存储，严禁明文保存密码。
- Lombok 可选；若使用，确保 IDE 和 Maven 编译配置正常。

前端：
- Vue 3 + Vite。
- TypeScript（建议开启，减少前后端字段对接错误）。
- Vue Router：用户端、管理员端路由管理。
- Pinia：登录用户、购物车、视频业务状态等全局状态。
- Axios：统一请求实例、Token 注入、错误处理。
- Element Plus：建议用于管理员后台表格、表单、分页、弹窗；用户端沉浸式页面不要直接套用 Element Plus 默认视觉。
- ECharts：数据统计图表。
- GSAP 或 Vue Transition + CSS：视频场景 UI 转场和微动效；按实际需要选用，不要堆叠多个动画库。

数据库：
- MySQL 8.x，统一字符集 utf8mb4。
- 数据库连接、账号密码必须放在 application.yml 的环境变量配置或本地私有配置中；提交项目时提供 application-example.yml，不提交真实密码。
- 提供完整 schema.sql 和可重复执行或明确说明执行顺序的初始化数据脚本。

版本规则：以上是技术选型约束，不要求为了追求最新小版本而盲目升级。Agent 开始前先检查本机 JDK、Maven、Node、MySQL 版本，选择彼此兼容的依赖版本，并将最终版本写入 README。

------------------------------
17.4 后端业务模块与接口要求
------------------------------

统一 API 前缀建议：/api/v1。
统一响应结构建议：
{
  "code": 0,
  "message": "success",
  "data": {},
  "timestamp": 0
}
分页接口统一返回 records、total、page、pageSize。错误响应必须提供可理解的 message；前端不得把后端异常堆栈直接展示给用户。

A. 认证与用户模块
- POST /api/v1/auth/register：用户注册。
- POST /api/v1/auth/login：用户登录。
- POST /api/v1/auth/logout：退出登录（如 JWT 无状态，仍需实现前端清理及必要的服务端失效策略说明）。
- GET /api/v1/users/me：当前用户信息。
- PUT /api/v1/users/me：修改个人资料。
- GET /api/v1/admin/auth/me：当前管理员身份与权限。
要求：注册时校验用户名/手机号/邮箱唯一性（按项目实际表单确定）；密码 BCrypt 加密；登录失败返回通用错误；接口校验身份和角色。

B. 菜品信息管理
- GET /api/v1/dishes：前台菜品列表，支持分类、关键词、价格区间、热量区间、上架状态、分页和排序。
- GET /api/v1/dishes/{id}：菜品详情。
- GET /api/v1/admin/dishes：后台菜品分页查询。
- POST /api/v1/admin/dishes：新增菜品。
- PUT /api/v1/admin/dishes/{id}：编辑菜品。
- PATCH /api/v1/admin/dishes/{id}/status：上架/下架。
- DELETE /api/v1/admin/dishes/{id}：逻辑删除优先，避免破坏历史订单。
菜品字段至少包括：id、name、categoryId、description、imageUrl、price、calories、protein、fat、carbohydrate、stock、status、recommendFlag、sortOrder、createdAt、updatedAt。
金额使用 DECIMAL，不得用浮点数直接进行金额运算。菜品营养数据应标记来源或估算属性，不得伪装成实验室精确测量。

C. 分类管理
- GET /api/v1/categories：前台启用分类。
- GET /api/v1/admin/categories：后台分类列表。
- POST /api/v1/admin/categories：新增分类。
- PUT /api/v1/admin/categories/{id}：修改分类。
- PATCH /api/v1/admin/categories/{id}/status：启用/停用。
- PATCH /api/v1/admin/categories/sort：调整排序。
分类字段至少包括：id、name、icon、sortOrder、status、createdAt。

D. 购物车与订单
- GET /api/v1/cart：读取当前用户购物车。
- POST /api/v1/cart/items：加入购物车。
- PUT /api/v1/cart/items/{id}：修改数量。
- DELETE /api/v1/cart/items/{id}：移除商品。
- POST /api/v1/orders：提交结算并创建订单。
- GET /api/v1/orders：当前用户订单分页列表。
- GET /api/v1/orders/{id}：订单详情。
- GET /api/v1/admin/orders：管理员订单列表和筛选。
- PATCH /api/v1/admin/orders/{id}/status：管理员更新订单状态。
订单状态建议：PENDING（待处理）、PREPARING（备餐中）、DELIVERING（配送/送餐中）、COMPLETED（已完成）、CANCELLED（已取消）。课堂演示可将送餐视频播放完成与订单状态更新串联，但必须区分真实业务状态和前端动画状态。

结算业务必须由后端完成：
1. 接收用户选择的菜品 ID 和数量，不信任前端提交的单价、总价和营养总量。
2. 后端重新读取菜品当前价格、上架状态和库存，校验库存充足。
3. 使用数据库事务创建订单和订单明细，扣减库存。
4. 保存订单明细的菜品名称、成交单价、数量等快照，防止菜品改价后历史订单跟着变化。
5. 返回订单号、订单金额、订单状态和订单明细。
6. 只有订单创建成功后，前端才允许播放 005-1 送餐视频；失败时保留购物车并提示原因，不得播放送餐动画。
7. 防止重复点击结算产生重复订单；使用按钮 loading、请求幂等标识或合理的业务校验。

E. 库存管理
- GET /api/v1/admin/inventory：库存列表。
- POST /api/v1/admin/inventory/adjust：库存调整，记录调整前后数量、原因、操作管理员和时间。
- GET /api/v1/admin/inventory/logs：库存流水。
库存为 0 或菜品下架时，前台显示售罄/暂不可购买，禁止加入购物车或提交订单。并发下单时必须在事务中进行库存校验与扣减，避免超卖。

F. 收藏与首页推荐
- GET /api/v1/favorites：当前用户收藏列表。
- POST /api/v1/favorites/{dishId}：收藏。
- DELETE /api/v1/favorites/{dishId}：取消收藏。
- GET /api/v1/recommendations/home：前台首页推荐。
- GET /api/v1/admin/recommendations：后台推荐配置。
- PUT /api/v1/admin/recommendations：调整推荐菜品、推荐标签和排序。

G. 营养分析
- GET /api/v1/nutrition/summary：当前用户营养摄入汇总。
- GET /api/v1/nutrition/trends：按日/周统计营养摄入。
- GET /api/v1/admin/nutrition/dishes：后台维护菜品营养信息。
营养统计应基于已完成或已确认订单明细与菜品营养数据计算，明确统计周期和计算口径。不要把推荐目标值误认为用户真实身体指标。

H. 数据统计分析（课程要求的必做模块）
必须使用 ECharts 在管理员后台提供可视化图表，不能只有几个数字卡片。
建议接口：
- GET /api/v1/admin/statistics/overview：今日/本周/本月订单数、销售额、客单价、菜品数量、用户数量。
- GET /api/v1/admin/statistics/orders-trend?period=week：订单量和销售额趋势。
- GET /api/v1/admin/statistics/dish-ranking?limit=10：菜品销量 TOP N。
- GET /api/v1/admin/statistics/category-sales：菜品分类销售占比。
- GET /api/v1/admin/statistics/hourly-distribution：各时段订单分布。
- GET /api/v1/admin/statistics/user-growth：用户增长趋势。
图表至少实现：
1. 近 7 天/30 天订单量与销售额折线图或组合图；
2. 菜品销量 TOP 10 横向柱状图；
3. 菜品分类销售占比饼图/环形图；
4. 一天内各时段订单量柱状图；
5. 核心指标卡片（订单数、销售额、客单价、用户数）。
图表必须从后端统计接口读取数据；开发阶段可用 SQL 初始化演示数据，但不允许在 Vue 组件内写死一组看起来像真实业务的统计数字。无数据时展示空状态和引导，不应绘制误导性图表。支持日期范围筛选或至少支持周/月切换。

17.5 MySQL 数据库设计要求
------------------------------

Agent 必须输出可执行的数据库建表脚本，并确保实体、Mapper、Service、Controller 与表字段对应。建议至少包含以下表：

1. sys_user：普通用户信息，用户名、密码哈希、昵称、手机号/邮箱、状态、创建时间。
2. sys_admin：管理员账号、密码哈希、角色、状态、创建时间。
3. dish_category：菜品分类。
4. dish：菜品基本信息、价格、图片、营养、库存、上架状态、排序。

6. shopping_cart：购物车主表（也可根据实现选择用户维度结构）。
7. shopping_cart_item：购物车商品及数量。
8. orders：订单主表，订单号、用户、总金额、状态、创建时间、完成时间。
9. order_item：订单明细快照，菜品 ID、菜品名称快照、成交单价快照、数量、营养快照。
10. inventory_log：库存调整流水、调整原因、操作人、调整前后数量。
11. home_recommendation：首页推荐配置、推荐标签和排序。
12. ai_conversation（可选但推荐）：用户 AI 对话会话。

数据库规范：

- 为订单号、用户名、分类 ID、菜品状态、创建时间等常用查询字段建立合理索引。
- 对用户收藏关系、订单号、用户名等设置唯一约束。
- 订单金额与历史商品信息使用快照字段。
- 提供 schema.sql、data.sql 或独立初始化脚本，至少包含管理员演示账号、普通用户演示账号、分类、6至12道菜品及足够生成图表的模拟订单数据。
- 演示账号和密码仅用于本地课堂演示，必须在 README 中明确标注；密码仍然需要 BCrypt 加密存储。不得把真实密钥、生产账号或个人隐私放入初始化脚本。

------------------------------
17.6 大模型结合方案（课程要求的必做展示点）
------------------------------

项目中的 AI 不应只是页面上放一个机器人图片或固定的聊天气泡。必须设计一个可交互的「AI 智能点餐助手」，让老师能现场输入自然语言并看到系统根据菜品数据库给出推荐。

推荐业务流程：
1. 用户在首页 AI 助手输入：“我今天想吃清淡一点，预算 20 元以内，最好有蔬菜，热量不要太高。”
2. Vue 将用户问题发送到 Spring Boot：POST /api/v1/ai/recommend。
3. Spring Boot 获取当前已上架、库存充足的菜品及其价格、营养和分类信息。
4. 后端将用户需求与菜品结构化数据组织为 Prompt，调用配置的大模型 API。
5. 大模型返回推荐菜品 ID、推荐理由、搭配建议及注意事项；后端必须校验模型返回的菜品 ID 确实存在、处于上架状态且有库存。
6. 前端展示推荐卡片，用户可以点击查看详情或加入购物车。

接口建议：
- POST /api/v1/ai/recommend：输入用户自然语言需求，返回推荐菜品、推荐理由和搭配建议。
- POST /api/v1/ai/chat：与 AI 助手进行多轮对话（可作为扩展）。
- GET /api/v1/ai/status：返回 AI 服务是否已配置、是否可用；不得返回 API Key。

AI 推荐约束：
- 大模型 API Key 只能保存在后端环境变量中，严禁写入 Vue 前端代码、浏览器请求或 Git 仓库。
- 将模型调用封装在独立 AiRecommendationService 中，避免 Controller 直接拼接第三方请求。
- Prompt 中提供真实的菜品候选数据，要求模型优先从候选菜品 ID 中选择，不允许编造菜名、价格或营养数值。
- 模型输出使用结构化 JSON 或明确的 DTO，并由后端进行解析和二次校验；解析失败时返回可理解的错误或降级结果。
- 必须有超时、异常处理和调用失败提示，不能让 AI 服务异常拖垮普通点餐功能。
- 如果课堂演示环境没有可用的大模型 API Key，提供一个清楚标注为“演示降级模式”的本地规则推荐服务：根据预算、热量、分类、关键词筛选数据库中真实菜品，并返回推荐理由。界面应明确标识当前为真实模型模式或规则演示模式，不能把规则推荐谎称为大模型生成。
- 记录必要的调用耗时和成功/失败状态即可；不要记录 API Key，不要无必要保存用户敏感信息。

AI 展示重点：让老师能够现场输入不同需求（如低脂、增肌、高蛋白、预算有限、想吃素），系统确实根据数据库菜品信息给出不同结果。AI 推荐必须与菜品管理数据联动，管理员新增或下架菜品后，候选范围应随之变化。

------------------------------
17.7 前后台视频业务与后端数据的边界
------------------------------

视频状态机仍然由 Vue 前端负责，后端负责用户、菜品、订单等业务事实。必须区分两类状态：

前端展示状态（Pinia 管理）：
- 当前视频段、当前视频播放状态、视频播放进度。
- 用户当前浏览的导航页签。
- 点餐镜头是否处于俯视菜单状态。
- UI 面板展开/收起状态。

后端业务状态（MySQL 持久化）：
- 当前登录用户。
- 购物车数据（如果采用后端持久化购物车）。
- 订单是否真实创建、订单状态、订单金额。
- 菜品是否上架、库存是否充足。
- 收藏关系和用户营养统计。

核心同步规则：
- 001-1、002-1、003-1、004-1、005-1、006-1 的播放顺序和触发条件继续遵循前文，不得因接入后端而改变。
- 003-1 结束后，用户处于“已落座、未下单、空桌”状态；点击点餐才切换到 004-1 俯视菜单镜头。
- 用户只加入购物车不代表订单创建成功，桌面仍然没有菜。
- 点击确认结算时先请求后端创建订单；后端返回成功后才播放 005-1。
- 后端创建订单失败时，停留在当前点餐状态，展示错误原因，桌面保持无菜。
- 005-1 完成后播放 006-1；用餐状态下固定显示图7场景，点餐入口提示“正在用餐，请珍惜粮食”，不允许重复创建本次用餐订单。
- 用户点击订单、收藏、营养管理等导航，只改变 UI 面板，不应错误重播场景视频。
- 页面刷新后应从后端查询订单和业务状态，并结合前端场景状态恢复；不得只根据 localStorage 中的一个布尔值判断订单成功。
- 如需把视频演示状态与订单关联，可在前端保存当前 session 的展示阶段，但订单是否成功必须以后端订单记录为准。

17.8 动态 UI 与前后端联动要求
------------------------------

保留原文档中的奶油白、鼠尾草绿、暖阳动漫场景风格和全站微动效要求。技术升级不能把用户端改成普通管理系统模板。

用户端：
- 视频背景使用本地项目静态资源，不需要通过后端逐帧传输视频。
- 登录、菜品列表、购物车、下单、订单、收藏、营养、AI 推荐均通过 Axios 调用后端 API。
- 菜品卡片、购物车数量、金额、库存状态、营养数值必须来源于 API 响应。
- 页面切换、导航、弹窗、卡片、图表和加载状态保留自然动画。
- 请求期间提供 skeleton/loading；失败时有重试和错误反馈；无数据时有空状态。

管理员端：
- 使用清晰、专业、易演示的后台布局：左侧导航、顶部用户信息和面包屑、主内容区。
- 采用表格、搜索筛选、分页、编辑抽屉/弹窗、状态标签、确认对话框。
- 新增/编辑菜品表单需包含名称、分类、价格、图片、描述、营养、库存、上架状态。
- 图片上传可先实现本地上传目录或受控静态资源上传，需校验文件类型和大小；不要让用户输入任意本机绝对路径。
- 管理员修改菜品、价格、库存、分类后，用户端重新请求 API 即可看到更新；必要时在操作成功后刷新对应数据。
- 管理后台图表数据来自统计 API，使用 ECharts；图表需适配窗口尺寸、支持日期切换、Tooltip 和图例。

------------------------------
17.9 统一异常、权限与安全底线
------------------------------

- 所有接口必须校验必要参数，后端使用 DTO + Validation，不直接将数据库 Entity 当作请求对象。
- 使用统一异常处理器，区分参数错误、未登录、无权限、资源不存在、库存不足、业务冲突和服务器异常。
- 普通用户只能查询和操作自己的购物车、订单、收藏及个人数据。
- 管理员接口使用角色权限校验；至少区分 ADMIN 与 USER。可扩展 SUPER_ADMIN、OPERATOR。
- 管理员新增、修改、下架菜品和库存调整必须经过后端权限检查。
- 防止越权访问：不能仅凭前端传来的 userId 查询他人订单。
- 密码必须 BCrypt 哈希；严禁明文存储或在日志中打印密码。
- SQL 使用参数化查询/ORM，避免 SQL 注入；文件上传校验类型、大小和文件名。
- CORS 仅允许本地开发前端地址或明确配置的来源，不要随意允许所有来源携带凭证。
- 大模型密钥、数据库密码均通过环境变量注入，不提交到仓库。
- 课堂演示数据必须明确是初始化模拟数据；统计页面不能声称它是真实运营数据。

十九、数据库实施手册：表结构、字段、约束与初始化数据（强制）
============================================================

本章优先级为 P0。Agent 不得只写“建立数据库并插入一些测试数据”，必须按本章交付可执行、可重复、可验证的数据库脚本。不得让前端自行维护一套与 MySQL 不一致的菜品数据。

19.1 数据库名称与基础约定

- 数据库名称：canteen_system。
- MySQL 版本：8.0 或兼容的 8.x。
- 字符集：utf8mb4；排序规则优先 utf8mb4_0900_ai_ci（若本机版本不支持，使用 utf8mb4_unicode_ci）。
- 所有时间字段使用 DATETIME 或 TIMESTAMP，统一按服务器时区保存，接口统一输出 ISO-8601。
- 主键统一 BIGINT；金额使用 DECIMAL(10,2)，禁止 FLOAT/DOUBLE 保存金额。
- 营养数值使用 DECIMAL(8,2)，单位在字段名或接口文档中明确。
- 状态字段使用 VARCHAR + 代码常量或 ENUM（二选一，全项目统一）；推荐 VARCHAR，便于扩展。
- 业务表至少包含 id、created_at、updated_at；支持软删除的表增加 deleted。
- 所有外键关系、唯一索引、普通索引必须在建表脚本中体现。
- 不允许把数据库密码、模型 API Key 写进 SQL、Git 或前端。

数据库创建命令：

CREATE DATABASE IF NOT EXISTS canteen_system
  DEFAULT CHARACTER SET utf8mb4
  COLLATE utf8mb4_0900_ai_ci;

19.6 订单、统计图表初始化数据（用于让老师看到真实 SQL 聚合结果）

不能只插入菜品而没有订单，否则统计图表会一直为空。初始化脚本或专用 DemoDataInitializer 应建立：
- 至少 2 个演示用户（student_demo 为主，另一个可选 demo_user_02）。
- 至少 30 笔演示订单，分布在最近 7 天内；其中状态至少包含 COMPLETED、DELIVERED、CANCELLED，销售额统计只统计项目定义的有效状态，取消订单不得计入销售额。
- 每笔订单 1～3 条 order_item，引用 D001～D012；订单明细必须写入名称、图片 URL、成交单价、数量、营养快照。

- 同步更新 dish.sold_count；如果初始化订单被定义为历史演示订单，库存也要保持逻辑一致（初始库存应是剩余库存，或在初始化时按订单销量扣减，二者只能选一种口径）。
- 至少写入 5 条 inventory_log，体现入库、售出扣减、人工调整等流水。
- 至少写入 6 条 home_recommendation 配置，引用有效且已上架的菜品。
- 统计接口必须从 orders/order_item 聚合，不得读取前端写死的图表数组。

推荐做法：将订单演示数据写成单独的 DemoDataInitializer，使用固定随机种子或固定明细列表，保证每次重置数据库后生成结果一致。初始化必须幂等：通过固定 order_no 前缀 DEMO- 检查是否已存在，存在则跳过；不能每次重启都重复生成 30 笔订单。

21.1 必须区分三种数据

A. 菜品基础数据：菜名、分类、价格、上架状态、库存、图片 URL。这些是点餐业务的核心数据，保存在 MySQL dish 表，由管理员后台维护。

21.4 管理员录入一道新菜品的完整操作

以管理员新增“香煎鸡胸藜麦饭”为例，流程必须是：
1. 管理员进入 /admin/dishes，点击“新增菜品”。
2. 输入菜名、分类、价格、描述、主要食材、过敏原、热量、蛋白质、脂肪、碳水、库存、标签。
3. 选择菜品图片；若没有图片，可先选择统一占位图并标记“图片待补充”，不能随便复用其他菜品图片。
4. 前端上传图片，取得后端稳定 URL。
5. 前端提交菜品 JSON 到 POST /api/v1/admin/dishes。
6. 后端校验分类存在、价格非负、营养字段非负、库存非负、图片 URL 合法；保存 dish 记录。
7. 同时创建库存初始流水，reason='INITIAL_STOCK'，记录操作管理员。
8. 若勾选上架，publish_status=PUBLISHED；若库存大于 0 则 supply_status=AVAILABLE，否则为 SOLD_OUT。
9. 用户端重新请求 GET /api/v1/dishes 后出现该菜品；首页推荐是否出现由 home_recommendation 决定。
10. AI 推荐候选集自动包含该菜品（前提：已上架、库存充足、营养信息满足筛选条件）。

21.5 数据导入、修改与重置原则

- 初始演示数据只通过 Flyway migration / DataInitializer 进入数据库，不在 Vue 组件里重复定义同一份菜品数组。
- 运行中的菜品新增、修改、上下架由管理员 API 完成，不允许直接改 SQL 作为日常操作。
- 修改初始化脚本不能覆盖已经存在的课堂演示业务数据；数据库迁移必须新增版本号，不可随意修改已执行的 Flyway 旧脚本。
- 重置演示数据必须提供独立脚本或命令，并要求用户明确确认；不得应用启动时自动清空数据库。
- 演示订单数据只在首次初始化时插入一次；重启服务不应重复生成。
- 真实订单、真实用户和演示种子数据要能通过 order_no 前缀、数据来源字段或专门标记区分。
